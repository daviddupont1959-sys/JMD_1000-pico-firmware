Motion Detector by Just Me Designs (JMD)
    This project is to create a motion detector which can send email messages to configured addresses in the event that no motion is detected after
     a configured time.
    It is meant to monitor that a person is actively moving in their environment, and alert loved ones if it appears they might have become unable to move
    It should be placed in a location that cannot detect a person if they have fallen in range of the detector,
     and could trigger it with arm movements or something like that.  The recommendation would be to plug it into a counter outlet in the kitchen area.
     The counter would block the detector from detecting the person on the floor even directly below the sensor.
    
    Two sets of email addresses can be configured
        A. Monitor email.  These addresses will receive an email daily to let the users know that the monitor is still operating.
        B. Alert email.  These addresses should be connfigured to generate text messages to the loved ones and will be sent when
           the configured timeout has occurred.  Most wireless carriers provide a special email address that will immediately send
           a test message to the subscriber.  For T-Mobile the address would look like this '6035983717@tmomail.net'

                    Alert reliability
                    - notify.send_inactivity_alert() now returns True only when ntfy.sh
                      answers HTTP 200, and never raises. It used to swallow every failure,
                      so a failed alert was lost forever (alert_flag was already set).
                      Alerts and "alert cancelled" notices are now queued and retried every
                      60 s until delivered. If an alert is cancelled before its notification
                      went out, both are dropped (logged) instead of sending a stale pair.
                    - How long the house has been quiet now survives a restart. The time of
                      last motion is saved to runstate.json (at most every 15 min; always after
                      a quiet spell of 1 h or more). After a restart it is restored if less
                      than 12 h old, so a reboot while the house is empty no longer silently
                      cancels the alert (previously ever_seen_motion reset to False and nothing
                      could fire until motion was seen). The saved time can only be earlier
                      than the truth, so the alert can come early after a restart, never late.
                    - The quiet timer is now an accumulated count of real elapsed milliseconds
                      (time.ticks_ms) and is reset only by motion. It is no longer reset when
                      the first sub-loop is re-entered, and it is immune to clock re-syncs and
                      DST jumps.
                    - A missing/invalid inactivity_alert falls back to 4 h, and an invalid
                      awake_window is treated as "awake", instead of raising TypeError.

                    MQTT is now best-effort (broker trouble can no longer stop monitoring)
                    - connect_mqtt() returns None on failure; it never raised. Detect.py
                      caught MQTTException, so an unreachable broker at BOOT crashed with
                      AttributeError ('NoneType' has no attribute 'publish') and, with the old
                      main.py, the Pico then sat idle until power-cycled. 3.03 also crashed
                      on the first motion seen during a broker outage (unguarded publish of
                      the new motion ON/OFF message). Now: boot continues without MQTT; every
                      publish goes through safe_publish() (never raises, drops the dead client);
                      reconnects are rate limited (MQTT 60 s, WiFi 120 s) so a long outage
                      cannot leave the PIR unread for long stretches.
                    - mqtt_callback() catches exceptions from command handlers, so a malformed
                      command on the public broker cannot crash the detector.
                    - Time/awake/alert publish and keep-alive ping use elapsed-time checks
                      instead of "time.time() % N == 0". Each loop pass takes a little over
                      a second, so the old test skipped the magic second fairly often; HA's
                      expire_after then flagged the sensors unavailable (the minute-aligned,
                      ~40%-of-the-day "unavailable" pattern seen in the HA history).
                    - publish_time() no longer reconnects by itself and returns True/False.

                    Crash recovery (main.py)
                    - Any exception from Detect.py (or Detect.py returning) is recorded in
                      crash.json and the Pico resets after 10 s, doubling per consecutive
                      crash up to 10 min. The next boot logs it (ERROR) and includes it in the
                      start-up push notification. The counter clears after 10 stable minutes.
                    - Create an empty file named debug.flag on the Pico to disable the reset
                      while developing. Ctrl-C is not intercepted.
                    - A failing OneTimeCode.py no longer prevents Detect.py from starting.
                    - NOT included: a hardware watchdog (WDT). The RP2040 WDT maxes out at
                      about 8 s and several calls (init_RTC, BLE window, HTTP) can block
                      longer; a WDT would risk reset loops. A hung (not crashed) Pico is
                      still possible - suggest an HA alert on the Time entity.

                    Other fixes
                    - Detect.py: missing/invalid HW_Config.json falls back to the original
                      pin assignments (and logs it) instead of aborting at boot.
                    - Sunday 02:01 clock re-sync (DST) is now checked every pass. It was only
                      evaluated after motion, so with nobody moving at 2 AM it never ran.
                    - iNet.connect(): a connection completing during the last wait second was
                      treated as a timeout.
                    - iNet.getDateTime(): the bound port-80 socket and the HTTP response were
                      not closed when the time request failed (later attempts could fail with
                      EADDRINUSE). Now always closed.

                    Logging (log_file levels)
                    - ERROR: HW_Config fallback; WiFi lost; MQTT lost (with reason); MQTT
                      unavailable at boot; notification failed (rate limited, with reason);
                      clock sync failed; command handler exception; bad config values;
                      previous run crashed.
                    - ALERT: ALERT Triggered! / ALERT cleared! (unchanged text, now at the ALERT
                      level so they survive a higher log_level); notification delivered; alert
                      cancelled before delivery.
                    - INFO: "Detector started. Firmware, reset cause"; config summary
                      (threshold, awake window); restored last-motion time; first motion since
                      start-up; motion after 1 h+ quiet; WiFi / MQTT restored (with outage
                      length); awake window opened/closed; weekly re-sync.
                    - DEBUG: hourly heartbeat "HB up= quiet= edges= seen= awake= thr= wifi=
                      mqtt= free=" (edges = PIR rising edges in the last hour: a high number
                      with nobody home means the sensor is false-triggering); clock syncs.
                    - Repeating errors are written at most once per interval so the 2 KB
                      files are not flooded. At DEBUG the hourly heartbeat limits history to
                      a few days; use INFO or ALERT for long retention.

                       normal operation. 2. Set inactivity_alert to 120 s: ALERT LED, push

                       gc.mem_free in the HB line is comfortably above 50K.

    2026/10/21 - Version 3.12  (one hardware config file for every unit)
                    FILES CHANGED: Detect.py, state.py.   NEW FILE: hwconfig.py (deliver it
                    together with state.py).   NEW HW_Config.json format (see below).

                    - hwconfig.py picks the unit's settings (client_id, motion pin, LED pins)
                      from ONE shared HW_Config.json by the board's unique ID
                      (machine.unique_id()), so the file no longer has to be copied per unit
                      and a dev board cannot pick up the real unit's identity (or the reverse).
                    - File format: {"default": <unit>, "boards": {"<board id>": <unit>, ...}}.
                      A board listed under "boards" uses its own entry. Any other board uses
                      "default" and the problem is reported: ERROR in the log and a note in
                      the start-up push notification, which includes the board's ID so it
                      can be added to the file.
                    - The 3.02-3.11 single-unit format (client_id/pins at the top level) still
                      works unchanged.
                    - A missing or unusable file falls back to built-in settings with a
                      warning. state.py also falls back to them if hwconfig.py is missing
                      (partial OTA), so the firmware can still start.
                    - Start-up log gains: "Hardware: board=<id> unit=<client_id>
                      config=<which entry> PIR=GPIO<n>".
